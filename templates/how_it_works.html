How Shikari works: its architecture, the libraries it builds on and where it uses AI

Shikari turns MITRE ATT&CK threat intelligence into detection queries for Microsoft Defender XDR, Google SecOps, Splunk and Elastic. Point it at a threat group, a CVE, a report or a company and it generates coverage for every technique involved, chains the detections into correlations, and checks them before you keep them. It is open source and self-hosted, and works without AI by default — a model is optional, and off unless you turn it on.

What it does

  • Detections for four SIEMs from one run
  • Hunt a group, CVE, report or technique
  • Cross-tactic attack correlations
  • IOC sweeps with an expiry
  • Company profiling and exposure mapping
  • A weekly, tagged threat feed
  • STIX, TAXII and MISP in and out
  • Detections as code, versioned in git
  • Threat library and red/blue assessments

How it works

  • ATT&CK procedures via MITRESaw
  • Indicator hygiene and a stack filter
  • Per-platform query builders
  • Static and precision checks before saving
  • Indicators checked against recorded telemetry
  • A saved Library, Coverage matrix and Flows

Optional AI

  • Off by default — never in the critical path
  • Local Ollama or a cloud provider
  • Ask Shikari, grounded in your data
  • Six agents (repair, ask, triage, sweep, audit, tune)
  • Threat briefings and report triage
  • Tools shared over MCP

Use it for

  • Threat hunting and detection engineering
  • Incident response preparation
  • Purple team exercises
  • SIEM content development
  • Closing coverage gaps against a named actor

Four ways in

  • The web UI (server-rendered, no JS framework)
  • shikari supervisor and console
  • shikari offline — no server needed
  • MCP, for any MCP client
  • Accounts, roles and MFA throughout

Frequently Asked Questions

What is Shikari and what does it do?

Shikari turns MITRE ATT&CK threat intelligence into detection queries for Microsoft Defender XDR, Google SecOps, Splunk and Elastic. Point it at a threat group, a CVE, a report or a company and it generates coverage for every technique involved, chains the detections into correlations, and checks them before you keep them. It is open source and self-hosted, and works without AI by default.

Do I need an AI provider to use Shikari?

No. Shikari works without AI by default, and the whole pipeline — generation, correlation and the checks — is deterministic code. AI is opt-in and never in the critical path: it adds Ask Shikari, the agents and threat briefings. When you do want it, you can point Shikari at a local model through Ollama or a cloud provider (Anthropic, OpenAI, Gemini, DeepSeek, Qwen, Grok), so nothing has to leave your machine.

What do I need installed? Does Shikari need Docker?

No. Shikari's core runs on Python alone — or in Docker, if you prefer — with nothing optional added: hunts, report analysis, company profiles and exposure maps, research, SIEM queries for all four platforms, ATT&CK and MITRESaw, Coverage, Flows, the Library, Detections as code, the threat feed, Cyber Powers, and IOC search with STIX, TAXII and MISP in and out. The maps are server-rendered and STIX/MISP need no extra libraries.

A few optional components are opt-in, and each is simply unavailable — never a broken app — when it isn't there. Shikari checks this host ({{ dependencies.host }}) each time you open this page:

Rocky 10 is Docker-only, so a host without Docker loses both Rocky and the Ubuntu container but keeps its Tart VM and the rest. An AI provider can also be a key you add under Profile → API Keys, which this host-level check doesn't see.

Why is Shikari so fast? Is it using AI or machine learning?

Generation is deterministic code, not model inference. The ATT&CK bundle and the OSINT rule index are built once and read from disk; indicators are matched with compiled patterns and dictionary lookups; queries come from per-platform builders, not token-by-token from an LLM; and correlation scoring is arithmetic over the techniques. A full group of 30–50 techniques takes minutes, and a single detection well under a second — and it all runs locally against a SQLite database, offline if you want.

When you turn AI on, it sits beside this, never inside it: Ask Shikari, the agents and briefings call a model you choose (local or cloud), and if one isn't configured the deterministic path is simply what runs. So the speed, the privacy and the repeatability are the default, and AI is something you add when it earns its place.

What's the difference between OSINT Enhancement and OSINT Comparison?

OSINT Enhancement: Automatically incorporates battle-tested detection patterns from OSINT sources (Elastic, Splunk community rules) directly into your queries. This is enabled by default on the Hunt and Analyse tabs. What LOLBAS, LOLRMM and LOLDrivers document about binaries, RMM tools and drivers the group is seen using is a separate option, LOL datasets, also ticked by default.

OSINT Comparison: Compares techniques against OSINT databases and adds metadata to YAML files (visible in the "Show Details" button). This is reference-only and doesn't modify the queries themselves. Either option adds the known false positives that Elastic and Splunk rules document for the technique (LoFP-style).

How do correlations work?

Correlations: Combines queries for the same SIEM (Google SecOps, Defender XDR, Splunk or Elastic) into multi-stage detections. This is enabled by default and helps create detection chains that track attack progressions within a single SIEM platform.

The results page shows each technique in a correlation as an individual query block, stacked with "chained with" connectors. The combined JOIN query is available via "Show Combined Query" below the stack.

How does Semantic Analysis work?

Semantic Analysis groups queries by behavioral categories (authentication, network, file activity, process execution, etc.) rather than just by technique ID. This is enabled by default and helps organize detections logically, making them easier to review, deploy, and maintain. It includes advanced query parsing for intelligent syntax-aware merging.

What file formats can Analyse read?

The Analyse tab reads multiple threat intelligence file formats including: PDF, TXT, Markdown (MD), JSON, CSV, Excel (XLSX/XLS), Word (DOCX/DOC), and YARA rules (.yar/.yara). Shikari automatically extracts TTPs (Tactics, Techniques, and Procedures) and IOCs (Indicators of Compromise) from these files.

What is the Profile tab used for?

The Profile tab lets you analyze an organization's threat landscape based on their domain. It automatically identifies industry-specific threats, geographic threat actors, technology stack vulnerabilities, and optionally supply chain dependencies. It then recommends relevant threat groups and can auto-generate detection queries for them.

What is Threat Briefing and how is it different from the AI Ask feature?

Threat Briefing generates a grounded, prioritised detection plan for a threat group. It is different from the Ask feature in a critical way:

  • Ask: Sends only the group name to the LLM — the LLM draws on its training data, which may be incomplete or outdated
  • Threat Briefing: Sends the actual MITRE ATT&CK technique list (all three attribution paths: direct, via software, via campaign) plus your current detection coverage — the LLM prioritises based on real data

What it produces

  • Coverage stats: How many techniques are already covered by your detection library vs. gaps
  • Top-N priority list: Ranked techniques with priority reasoning and specific detection approach per technique
  • Attack chain: Kill chain tactic progression for the group
  • Executive summary: 2–3 sentence briefing for SOC leadership

How to use it

  1. Enter a threat group name in the Generate tab (e.g., "Scattered Spider")
  2. Click Threat Briefing (the button below Generate Detections)
  3. Select the number of top techniques to prioritise (5 or 10)
  4. The briefing panel loads with coverage statistics, the ranked technique cards, and the attack chain

Requires: An LLM configured (Anthropic, OpenAI, or local Ollama). The briefing uses POST /api/threat-briefing and passes the complete technique/coverage context to the model.

What are the individual query blocks on the results page?

After generating detections and correlations, the results page now shows individual detection queries per technique within each correlation, stacked visually with "chained with" connectors between them. This replaces the previous single combined-query view.

What you see

  • Technique name — the MITRE ATT&CK technique name
  • ATT&CK ID badge — e.g., T1078 in a blue pill
  • Tactic badge — e.g., Initial Access in a green pill
  • Query block — the individual Splunk SPL or KQL query for that technique
  • Copy button — copies the individual query to clipboard
  • "chained with" connector — visual divider between techniques in a correlation

Combined query

The JOIN query that combines all techniques is still available — click Show Combined Query below the stacked blocks to expand it. This is the query you deploy to your SIEM as a single multi-stage alert.

Why this matters

Previously you could only see the combined JOIN query. The individual blocks let you understand exactly which technique each sub-query detects, copy individual queries for testing, and understand the attack chain before deploying the combined rule.

How fast is Shikari at generating detections?

Shikari is optimized for speed with template caching, parallel processing, and async operations. Generating 200 detection queries for a threat group like APT29 takes approximately 30 seconds with caching enabled (compared to 4-5 minutes without optimization). First-time runs take about 45 seconds while subsequent cached runs complete in about 5 seconds.

What output formats does Shikari generate?

Shikari generates multiple output formats:

  • YAML files: Individual detection rules in standardized YAML format
  • Vendor queries: Splunk SPL and Microsoft KQL queries
  • Correlation JSON: Multi-stage detection relationships
  • Attack Flow diagrams: JSON and HTML visualizations following the MITRE ATT&CK Flow specification
  • Library view: Interactive web interface to browse and export detections
Can I customize the generated detection queries?

Yes! All generated detections are saved as YAML files that you can review, modify, and customize before deploying to your SIEM. The queries are designed to be production-ready but should always be tested in your environment and tuned to reduce false positives based on your specific infrastructure.

How do I customize mapping files for my environment?

Shikari uses three mapping files to control detection generation for different environments:

  • indicatorMapping.json: Maps indicator types (cmd, file, ip, domain, etc.) to data sources and fields
  • platformMapping.json: Defines which platforms (Windows, Linux, AWS, Azure) are supported by each data source
  • fieldMapping.json: Maps generic field names to vendor-specific field names (e.g., process_name → ProcessName for Defender XDR)

Common customization scenarios:

  • Using custom Splunk indexes: Update indicatorMapping.json to replace default indexes with your own (e.g., index=custom_windows_logs)
  • Multi-cloud environments: Add AWS/Azure/GCP data sources to appropriate indicator types
  • Custom EDR solutions: Add new vendor mappings for CrowdStrike, Carbon Black, SentinelOne, etc.
  • Disabling unused sources: Remove or comment out data sources you don't have

Best practices: Always backup mapping files before modifying, validate JSON syntax, test with small groups first, and document your changes. See the Mapping Files Configuration Guide for detailed instructions and examples.

What data sources does Shikari pull from?

Shikari pulls from multiple authoritative sources:

  • MITRE ATT&CK: Official enterprise-attack.json for technique mappings
  • Community repositories: Elastic detection rules, Splunk security content
  • OSINT sources: 5+ open-source security repositories with 7,500+ detection rules
  • Threat reports: Uploaded files or analyzed blog posts/reports
Is Shikari suitable for production use?

Shikari generates production-quality detection queries, but as with any automated tool, you should review and test all detections in your environment before deploying to production. Different organizations have different baselines, and tuning is essential to reduce false positives and ensure the detections work correctly with your specific data sources and infrastructure.

How do I get started with Shikari?

Getting started is easy:

  1. Go to the Generate tab and enter a threat group name (e.g., "APT29") or MITRE technique ID
  2. Optionally enable AI, with a local Ollama model or a cloud provider, in Profile → API Keys
  3. Click "Generate Detections" and wait for processing to complete
  4. Download the generated detections as a ZIP file
  5. Review the YAML files and deploy queries to your SIEM
Does Shikari work offline?

Shikari requires internet access for the initial setup to download MITRE ATT&CK data and OSINT repositories. Once cached, it can generate detections offline without requiring external API calls (unless you enable AI enhancement). All OSINT sources are cloned locally, so Shikari doesn't rely on external APIs for core functionality.

How does Shikari handle software (malware/tools) in threat groups?

Shikari uses software-to-technique traversal to extract actionable indicators from malware and tools. Instead of just detecting software names like "BlackCat" or "Mimikatz", Shikari automatically:

  1. Identifies which techniques the software employs (e.g., BlackCat uses T1083 File Discovery, T1486 Data Encryption)
  2. Extracts technical indicators from those techniques (e.g., net use, fsutil behavior set)
  3. Merges these with the group's direct technique indicators
  4. Removes duplicates to create comprehensive detections

Example: For Scattered Spider using BlackCat ransomware, detections include specific commands BlackCat runs (like fsutil, vssadmin) rather than just looking for the "BlackCat" string.

This implements two indicator extraction paths:

  • Direct: Group → Techniques → Indicators
  • Software: Group → Software → Techniques → Indicators
How are correlations scored and prioritized?

Shikari scores correlations on a 140-point scale based on six key factors:

  • Technique Criticality (30 points): High-impact techniques like credential dumping, lateral movement, and data exfiltration score higher
  • Tactic Priority (20 points): Correlations involving critical tactics (Credential Access, Lateral Movement, Exfiltration, Impact) score significantly higher than lower-priority tactics (Execution, Discovery)
  • Query Specificity (20 points): More specific queries with detailed indicators score better than generic ones
  • False Positive Rate (25 points): Lower estimated false positive rates increase the score
  • Attack Progression (25 points): Correlations that follow logical attack chains (e.g., Credential Access → Lateral Movement) score highest
  • Data Source Diversity (-10 to +20 points): Correlations spanning multiple data sources (e.g., process + network) get bonus points

Tactic Priority Weights:

  • Critical (10 pts): Credential Access, Lateral Movement, Exfiltration, Impact
  • High (8 pts): Privilege Escalation, Persistence, Command & Control
  • Medium (6 pts): Defense Evasion, Collection, Initial Access
  • Lower (3-4 pts): Execution, Discovery, Reconnaissance

Note: Semantic overlap (query field similarity) is calculated and displayed as informational metadata but does NOT affect scoring. What matters is whether the techniques form a meaningful attack chain, not whether they use similar log fields.

Minimum Threshold: Only correlations with 75% or higher relevance (score ≥ 105/140) are included by default. This threshold can be adjusted by setting CORRELATION_MIN_RELEVANCE in your .env file (range: 0.0 to 1.0).

How does Shikari handle multi-cloud environments (AWS/Azure/GCP)?

Shikari includes sophisticated cloud platform separation to prevent mixing AWS, Azure, and GCP indicators incorrectly:

  • Cloud-native logs: AWS CloudTrail, Azure Activity Log, and GCP Audit logs are only used for their respective cloud platforms
  • Endpoint detection: Endpoint logs (Windows, Linux, Defender XDR tables) can detect cloud CLI tools running on endpoints (e.g., aws, az, gcloud commands)
  • Automatic filtering: Detection queries automatically select appropriate log sources based on cloud platform context
  • No cross-contamination: AWS API calls won't generate Azure AD detections, and vice versa

This ensures clean, platform-specific detections while maintaining the ability to detect cloud CLI usage on endpoints.

How do correlation filters work?

Shikari uses multiple intelligent filters to ensure only high-quality correlations are generated:

  • Attack Progression Filter: Only correlates techniques that follow logical kill chain sequences (e.g., Initial Access → Execution → Privilege Escalation)
  • Semantic Overlap Filters: Removes near-duplicates (>75% overlap) and completely unrelated pairs (<20% overlap)
  • Same-Table Deduplication: Prevents low-value correlations between detections querying identical data sources
  • High-Impact Requirement: Prioritizes correlations involving at least one high-value MITRE ATT&CK technique
  • Data Source Diversity: Awards bonus points to correlations spanning multiple data sources for better coverage
  • Correlation Grouping: Automatically deduplicates similar technique pairs, keeping only the highest-quality correlation

Result: 75-85% reduction in correlation noise while maintaining attack chain detection fidelity.

What is "Merge by Tactic" and when should I use it?

Merge by Tactic combines all detections under the same MITRE ATT&CK tactic (e.g., all Credential Access techniques), then correlates across tactics.

When to use:

  • Executive dashboards requiring simple, high-level view
  • Low-noise alerting for SOC environments
  • Phase-based threat hunting campaigns
  • Incident response workflows focused on attack progression

Benefits:

  • Generates 8-15 high-level correlations instead of hundreds
  • Represents entire attack phases (e.g., "All Credential Access → All Lateral Movement")
  • Broader detection coverage - catches ANY technique in the tactic
  • Reduces alert fatigue significantly

Trade-off: Less granular - you won't see which specific techniques triggered, but you'll know which attack phases occurred.

What is "Merge by Parent Technique"?

Merge by Parent Technique groups subtechniques under their parent (e.g., T1003.001, T1003.002, T1003.003 → T1003), then correlates parent techniques.

When to use:

  • Mid-level granularity between tactic-level and subtechnique-level
  • Tracking specific attack patterns without excessive detail
  • Correlating technique families (all OS Credential Dumping methods)

Benefits:

  • Moderate correlation reduction (~50-70% fewer than default)
  • Maintains technique-level context
  • Groups related attack methods logically
  • Good balance between detail and simplicity

Example: Instead of 9 correlations for every LSASS dumping variant, you get 1 correlation for "OS Credential Dumping (T1003)".

How can I test which correlation settings work best for me?

Shikari includes a test script to evaluate different filter combinations:

python test_correlation_filters.py "Scattered Spider"

The script will:

  • Run correlations with baseline, merge-by-tactic, and merge-by-parent modes
  • Compare total correlation counts
  • Calculate average relevance scores
  • Identify high-quality correlation counts
  • Measure execution time for each configuration
  • Provide recommendations based on your specific threat group

Results are saved to a JSON file for further analysis. Use this to determine which mode produces the most actionable results for your environment.

What are the various approaches to building correlations available in Shikari and how do I invoke each one?

Shikari uses one correlation engine that automatically runs after detection generation. However, you can influence the quality of correlations by choosing different detection generation modes:

The Correlation Engine (Always Enabled)

Shikari's correlation engine uses a rule-based heuristic scoring system with 6 factors (0-140 points) to intelligently pair detections within each vendor. This engine:

  • Automatically runs after detection generation completes
  • Cannot be disabled (always generates correlations)
  • Works entirely offline without AI
  • Provides deterministic, consistent results
  • Includes semantic analysis by default: Calculates semantic overlap between queries (0-100%) to filter duplicates and ensure diversity

Scoring factors: Technique Criticality (0-30 pts), Tactic Priority (0-20 pts), Query Specificity (0-20 pts), False Positive Rate (0-25 pts), Attack Progression (0-25 pts), Data Source Diversity (-10 to +20 pts)

Built-in semantic analysis: Always calculates token-based semantic overlap (Jaccard similarity) to filter correlations with >80% overlap (too similar)

Tunable parameters (Profile → Config):

  • Threshold: 40% (minimum relevance score to include correlation)
  • Per-Vendor Limit: 60 (max correlations per vendor)
  • Tech Frequency: 20 (max appearances of a technique in simple correlations)

Detection Generation Modes (Affect Correlation Quality)

The quality and types of correlations depend on what detections you generate. Choose a generation mode:

1. Standard Generation (Default)
  • How to invoke: Don't check any boxes (default)
  • What it does: Generates detections using template-based approach
  • Correlation result: Standard correlations based on templates
2. Advanced Parsing (Semantic Analysis)
  • How to invoke: Check "Advanced Parsing" in Web UI
  • What it does: Groups detections by behavioral categories during generation (authentication, network, file, process)
  • Correlation result: More semantically-related correlations that understand behavioral context
  • When to use: Complex attack chains where behavioral relationships matter
3. AI Generators (Optional)
  • How to invoke: Check "AI Generators" checkbox in Web UI
  • What it does: Uses LLMs to enhance detection generation quality
  • Effect on correlations: AI-enhanced detections → better quality input for correlation engine
  • AI providers: a local model via Ollama or LM Studio, or a cloud provider (Anthropic, OpenAI, Gemini, DeepSeek, Qwen, Grok)
  • Requirements: a provider configured in Profile → API Keys, or a local LLM endpoint for offline AI
  • When to use: Experimental AI-enhanced detection quality
4. AI Correlations (Optional)
  • How to invoke: Check "AI Correlations" checkbox in Web UI (requires "AI Generators" also enabled)
  • What it does: Uses LLMs to improve correlation JOIN query combination strategies
  • What it does NOT do: Detection pairing and scoring remain rule-based (6-factor, 0-140 points). AI cannot change which detections get paired or their relevance scores
  • Effect on correlations: Smarter JOIN query logic for combining detection queries
  • Requirements: AI enabled, with a provider configured in Profile → API Keys
  • When to use: Experimental AI-enhanced correlation query combination

The generation pipeline

An input — a threat group, a CVE, a report or a company profile — resolves to ATT&CK techniques, and each stage narrows raw intelligence into a detection that will actually fire:

  1. Procedure retrieval — the techniques and their procedure examples, from the ATT&CK STIX bundle via MITRESaw.
  2. Extraction, hygiene and stack filter — indicators are pulled and cleaned (placeholders, generic words and known-good values removed), and anything outside the platforms and products you run is dropped.
  3. Query builders — one per platform: Defender KQL, SecOps YARA-L, Splunk SPL and Elastic.
  4. Validate and save — queries that parse but can't fire are removed; the rest join the shared YAML library.
  5. Correlation engine — chains detections across tactics on one host or account within a time window.
  6. IOC sweeps — a branch off a report or CVE: indicator sweeps with an expiry.

Optional AI sits alongside the pipeline, never in its critical path: Ask Shikari and the agents, driven by a local Ollama model or a cloud provider only when you enable them.

The same pipeline from a terminal

shikari is the supervisor — start, status, restart, mcp, console — and the console and offline modes run the identical stages without a browser. A few surfaces are web-only (the saved Library, the Coverage matrix and Flows); everything else is reachable from the command line.

Without a server at all

# The pipeline with no server running
shikari offline generate "APT29"      # detections for a threat group
shikari offline hunt T1003.001        # one technique, by name or ID
shikari offline correlate "APT29"     # correlation rules

# The supervisor and interfaces
shikari start | status | restart      # run the server
shikari console                       # the modules interactively
shikari mcp                           # Shikari's tools for any MCP client

Detections as code

A run's detections are files, so they belong in version control. Detections → Detections as code commits a group's detections to a git repository at stable paths, so a Regenerate after an ATT&CK release becomes a commit whose diff is exactly the queries that were added, removed or changed. Point a remote at it and push anywhere. Pushing into a SIEM's own rule store (Defender XDR, Google SecOps) is a dry run for now — the payloads are built, nothing is sent, and a rule would be created disabled.

Backend and storage

State is a single SQLite database. The intelligence the pipeline draws on is context, not input: the ATT&CK bundle and MITRESaw, NVD and public PoCs, the OSINT rule index (Elastic, Splunk, Sentinel and SecOps public rules with their documented false positives), LOLBAS/LOLDrivers/LOLRMM, known-good lists, recorded attack telemetry and Microsoft's Defender XDR GUIDE grades.

Shikari generates attack flow diagrams following the MITRE ATT&CK Flow specification. These visualizations show technique sequences and attack paths.

ATT&CK isn't linear. Its tactics are an adversary's goals, not steps in a fixed order: a group can reach Discovery before Execution, return to Credential Access after Lateral Movement, or skip tactics altogether. Shikari lays tactics out left to right in ATT&CK's usual order for reading, but never treats that order as the sequence a group followed. The order that matters is the one the correlation links show: one technique seen before another on the same host.

The results page's attack flow has three tabs over the same techniques: MITRE ATT&CK (by tactic, where you rearrange and link them), the Cyber Kill Chain (Lockheed Martin) and the Targeted Attack Lifecycle (Mandiant). A technique goes by its tactic, or by the technique itself where that says more, such as phishing as Delivery. The mapping is Shikari's own (shikari/visualization/frameworks.py), since neither model has an official ATT&CK crosswalk.

Example flows

Correlation flow. One multi-stage correlation on a single host — phishing lands, PowerShell runs, LSASS is read, data leaves over the C2 channel. The arrows are the correlation links, not ATT&CK's tactic order: this is the sequence actually seen.

Complete actor flow. All of a group's techniques and the routes between them. Execution branches to Discovery and Credential Access, and the dashed amber edge is a non-linear return — back to Credential Access after Lateral Movement. Tactics read left to right; the paths do not have to.

Emulate checks a detection against logs recorded while attacks were actually run in a lab. For each technique it shows whether a detection's indicators appear in real recorded events, and by which log — a cheap first look before testing against your own SIEM. No AI, no infrastructure; it reads values the pipeline already matches on.

StatusWhat it means
SeenThe detection's indicators appear in recordings of its own technique — it would have matched real events, and this says which log it needs.
Not seenThe technique has recordings, but none contain the indicators. Not proof it's wrong — the recording may have used another tool or procedure.
No recordingsNo source recorded the technique.
NoisyAn indicator recorded in five or more other techniques too — it matches the lab's ordinary activity as well as the attack.

The same noise check is a tool, noisy_indicators, for the agents and any MCP client. The Library audit agent uses it to flag weak detections and Detection tuning to tighten them; Ask Shikari has it too.

From checking logs to recording tests

Emulate tells you which logs could record a technique; Assessments (Build → Assessments) record what actually happened when you tested. Build a threat library of test cases from a profile's ranked groups — one per MITRESaw procedure, sorted by how many of those groups use the technique — then run them in a campaign, logging a red outcome (executed, failed, blocked) and a blue outcome (not logged, logged, alerted, prevented) per technique. A logged-but-no-alert result links straight to a detection hunt; outcomes export as CSV or an ATT&CK Navigator layer. VECTR-style, per user, no AI.

What AI Enhances

1. Enhanced IOC Extraction

Without AI: Regex-based pattern matching (fast but rigid)
With AI: Contextual understanding of indicators 

Example:
Input: "The adversary used rundll32.exe dump) or (.exe .dll dump)))"
Regex: Extracts literal string with syntax errors
AI: Understands this is "rundll32.exe dump" with malformed syntax

2. Semantic Query Grouping

Without AI: Keyword-based categorization
With AI: Behavioral understanding 

Example Grouping:
Authentication Group:
- "Login attempts from ServiceAccount"
- "Kerberos ticket requests"
- "NTLM authentication failures"

AI understands these are related behaviors, not just keyword matches

3. Correlation Analysis

Without AI: Technique ID proximity
With AI: Multi-stage attack pattern recognition 

Example:
T1078 (Valid Accounts) + T1021 (Remote Services) + T1003 (Credential Dumping)

AI recognizes this as:
"Lateral movement attack chain:
 Compromise credentials → Access remote systems → Dump more credentials"

Agents

An agent is a model in a loop with tools: it picks a tool, reads the result, and picks again until it can answer. The model never runs anything itself; Shikari runs the tool it asks for and sends the result back. Tools that change something (hunts, saving a query) wait for your approval.

AgentPatternWhat it does
Detection repairCheck, fix, check again Static checks over a run's queries (Defender XDR schema, SecOps UDM search structure, SPL structure); fixes what fails, re-checks, saves with a reason. A query that still has errors can't be saved.
Ask Shikari (agent)Look it up Answers from coverage, results, ATT&CK and the library instead of memory; checks any query it writes; can start hunts.
Intel triagePlan across steps Report → techniques and IOCs → coverage gaps → hunt → briefing.

Run them from the Agents page, the console (use agent/repair) or any MCP client: shikari mcp exposes the same tools and the agents' prompts to Claude Code, Claude Desktop or your own agent. examples/agents/minimal_agent.py is a complete agent in about 100 lines. Full guide: docs/agents/README.md.

An agent is a model in a loop with Shikari's tools: it picks a tool, reads the result and picks again until it can answer. Every step is shown as it happens and kept, so you can read back what it did. Agents run on any provider in your profile that can call tools; Claude is the most reliable at multi-step tool use, and small local models often stop early. Intel

The Intel menu is where threat intelligence comes into Shikari before it becomes detections — the weekly feed, the companies you've profiled, and the report and actor research that seeds a hunt.

Threat Feed

This week's threat research, pulled from around 26 vendor and government sources and tagged by industry, nation and motive. Watchlists flag new posts about the groups, sectors or regions you care about, optionally by email, and your technology-stack filter highlights what's relevant to what you run.

Indicator Management

One page for indicators, in two tabs. Search indicators looks up an IP, domain, URL, hash, email or CVE — and its common defanged forms — across the reputable vendor, CERT/government, news and aggregator sources from the last 7 days, filterable by tier and cached for the window. No AI.

Import / export takes intelligence in the other direction: STIX bundles, TAXII collections and MISP events arrive as often as blog posts, so Shikari takes those as a hunt input too — by file upload, pasted JSON, a polled TAXII collection, or a pull from a MISP instance (/events/restSearch with an API key, used for that request only). Attack-patterns become techniques, indicator patterns and observables become IOCs, and an intrusion-set names the group — the same review-then-generate path as a report. A finished run exports the other way, as a STIX 2.1 bundle (detections carried as x-shikari-detection objects) or a MISP event (techniques as ATT&CK galaxy clusters, IOCs as attributes). Both round-trip. No AI.

Companies Catalogue

Every organisation you've profiled, newest first — a Library for companies. Each card opens that company's exposure map and Review page, so a profile doesn't have to be re-run.

Report and actor research

Extract TTPs and IOCs from a report URL or file and hunt them, or find groups by keyword (country, industry) and consolidate their techniques before generating coverage.

Company profiling

Profiling starts from a company instead of a threat: enter a domain and Shikari works out who is likely to target it, then generates detections for the groups you choose. It reads Wikidata, the company's homepage and OSINT to establish its sector, where it operates and where its site is hosted, and fingerprints the technology stack for relevant CVEs — all in the background, with a progress page of its seven stages.

The Review page

When profiling finishes it opens a Review page: the company's branding, a profile summary (industry, location, hosting, source, risk score), the exposure map, and the recommended groups laid out in columns — each with a likelihood of targeting this organisation (how strongly its sector and region match the group's known targeting), the top three pre-ticked. Tick the groups you want and generate; each gets its own Results page.

Organisation Exposure Map

A node-and-link graph of everything profiling surfaced from public sources and how each piece links back to the domain — the attack surface a threat actor sees before acting. Two hops out: resolved IPs, nameservers, mail, subdomains, technology and historical snapshots off the domain; then the networks, certificates, exposed services, known CVEs and breach surface off those.
