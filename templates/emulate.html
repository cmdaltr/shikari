Generating telemetry

Recordings are real attacks run in a lab with logging on — the public datasets that ship with Shikari, plus any you record yourself in Lab below. Each is mapped to ATT&CK, then Shikari checks whether the indicators your detections match actually appear in the recorded events. The result is the Recorded telemetry views below, organised by technique, group or data source. No AI is involved.

Public datasets

    Each recording is one tool run in a lab with logging on (Sysmon, Windows auditing, PowerShell, cloud audit logs), mapped to ATT&CK by the people who recorded it. It shows that a technique can be recorded and by which log, for that tool in that lab; not every way the technique can be done. The recordings ship with Shikari; Update (or python -m shikari.telemetry --build) fetches what the sources have changed since.

    
  
    

  
  
    
      
    Your lab
    
      
    Install, create and manage the containers and VMs an emulation records on, without leaving Shikari.
        Shikari drives Docker and Tart to create Linux and macOS machines, and UTM for Windows (and other OSes QEMU runs) — you build the UTM VM once, then Shikari manages it. On a Windows host it drives Hyper-V, and on a Linux host KVM through libvirt: both create a Linux VM from Ubuntu's cloud image, or a Windows VM from your own disk image or ISO.
        The machines are disposable — snapshot one before you turn logging on or run atomics, and revert when you're done.
        A running machine has Console (an interactive shell in the browser) and Desktop (a graphical console — VNC or SPICE) — the Desktop panel asks for the machine's endpoint and protocol the first time, since UTM's display can't be auto-discovered.
