Confidence of Detection

Each detection includes a confidence score indicating the estimated probability of successful detection. This likelihood percentage is calculated based on:

  • Indicator Strength - Quality and specificity of indicators (file paths, registry keys, command-line patterns, network signatures)
  • Data Source Availability - Whether the required log sources are commonly available in enterprise environments
  • Query Specificity - How precisely the detection targets the technique versus generating potential false positives
High (75-100%) Medium (50-74%) Low (0-49%)

How Detections are Generated

Archer generates detections through an automated pipeline that transforms threat intelligence into actionable security rules:

  1. MITRE ATT&CK Extraction - Retrieves technique descriptions, procedure examples, and software/malware behaviors from the MITRE ATT&CK framework
  2. Indicator Parsing - Extracts specific indicators including file paths, registry keys, command-line patterns, process names, network indicators, and behavioral signatures
  3. Generic Filtering - Removes overly broad terms (e.g., "file", "process", "command") that would generate excessive false positives
  4. Vendor Translation - Converts indicators into platform-specific query languages (Splunk SPL, Defender XDR KQL, etc.) using custom mapping files
  5. OSINT Enrichment (Optional) - When MITRE indicators are insufficient, searches additional threat intelligence sources to enhance detection coverage
  6. YAML Construction - Packages the detection as a standardized YAML file with metadata, tags, references, and query logic

How Correlations are Compiled

Actor correlations combine multiple data points to build comprehensive detection coverage for threat groups:

  1. Direct Procedure Examples - Extracts indicators from techniques explicitly used by the threat actor in documented campaigns
  2. Software/Malware Attribution - Identifies software and malware families associated with the actor, then retrieves indicators from those software pages even when direct actor-to-indicator links aren't documented
  3. Transitive Relationships - Maps relationships like Actor → Uses Software → Implements Technique → Has Indicators, building detections from the complete chain
  4. Multi-SIEM Coverage - Generates detections for Google SecOps, Defender XDR, Splunk and Elastic to ensure broad deployment options
  5. Deduplication & Merging - Combines similar detections targeting the same technique to reduce noise and improve query efficiency
  6. Confidence Scoring - Assigns likelihood scores based on indicator quality and the strength of attribution between actor, software, and technique

Example: If an actor uses a specific malware family, but that malware's MITRE page shows technique implementations without direct indicators, Archer will search the malware's software page for indicators, then construct detections that link back to the actor through the software relationship.

Important Notes

  • Review Before Deployment - All generated detections should be reviewed and tuned for your environment before production deployment
  • False Positives - Detection rules may require adjustment to reduce false positives based on your organization's baseline activity
  • Data Source Requirements - Ensure required log sources (process creation, registry changes, network traffic, etc.) are available and properly configured
  • Indicator Freshness - MITRE ATT&CK and OSINT sources are updated periodically; regenerate detections regularly to incorporate new intelligence
  • Vendor-Specific Syntax - Queries are optimized for each platform's query language and data model; cross-platform translation may require additional validation

Validation

Expand
Step 1: Review Detection Logic

Verify that each query's logic matches the technique description and would catch the intended attack behavior.

View Guidance
  • Does the query logic align with the MITRE ATT&CK technique description?
  • Are the indicators appropriate for detecting this technique?
  • Would this query catch actual attack behavior?
  • Review any OSINT enrichment data for additional context
Step 2: Test Query Syntax

Copy queries to your SIEM and verify they execute without syntax errors and complete in reasonable time.

View Guidance
  • Run the query in your SIEM environment
  • Verify no syntax errors occur
  • Check query performance (recommend <30 seconds execution time)
  • Test across your configured time ranges
Step 3: Validate Field Names

Confirm that field names and index/source names match your actual log schema.

View Guidance
  • Verify field names match your log schema (e.g., process_name vs ProcessName)
  • Check that index/source names are correct for your environment
  • Update your mapping files if needed (see profile page)
  • Ensure data sources are actively collecting logs
Step 4: Assess False Positive Risk

Review query specificity and identify any benign processes or patterns that may need exclusions.

View Guidance
  • Is the query too broad? Consider tightening criteria
  • Identify benign processes that match the pattern (e.g., admin tools)
  • Add exclusions for known-good processes/paths if needed
  • Test in monitoring mode before enabling alerting
  • Consider environment-specific tuning (dev vs prod)
