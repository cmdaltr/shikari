# Query Execution

Running a generated query against the SIEM and reading the results back.

## Splunk

`shikari/query/splunk.py` (`SplunkClient`) runs SPL through Splunk's search jobs API on the management port (8089) and reads the results back a page at a time. There's no page or CLI command that runs it yet; Detection Validation's Splunk instances use it (`shikari/validation/docker_manager.py`).

```bash
export SPLUNK_HOST=splunk.example.com
export SPLUNK_TOKEN=...                 # Settings > Tokens; or SPLUNK_USERNAME and SPLUNK_PASSWORD
export SPLUNK_PORT=8089                 # the default
export SPLUNK_VERIFY=1                  # check the certificate; off by default for a lab's self-signed one
```

```python
from shikari.query.splunk import SplunkClient

r = SplunkClient().execute_query(spl, earliest_time="-24h", max_results=0)   # 0: every result
if r["status"] == "success":
    rows, stats = r["results"], r["stats"]   # stats: row_count, result_count, truncated, scan_count, run_duration
else:
    print(r["error"])                        # Splunk's own message
```

- **Authentication**: a token goes as `Authorization: Bearer`; a username and password get a session key, renewed once if it expires mid-run.
- **SPL**: a bare search gets the `search` command in front; one starting with `|` (`| tstats`, `| makeresults`) is sent as written. A time term in the SPL (`earliest=-1d`) wins over `earliest_time`.
- **Paging**: `page_size` results per request (1,000 by default) until `max_results` or the job's result count; `stats.truncated` says when `max_results` cut it short.
- **Errors are returned, not raised**: bad SPL (Splunk's parser message), an expired or revoked token, a failed job, a timeout (the job is cancelled), Splunk unreachable. 429 and 503 are retried three times, honouring `Retry-After`.

### Validated

Against Splunk Enterprise 10 (the Docker image, trial licence) on the homelab, 10 November 2026 ([#44](https://github.com/cmdaltr/shikari/issues/44)), from inside Shikari's container: token and password authentication; a detection generated by `compile_splunk_queries` for T1082 run over the Windows 11 lab recording (Sysmon 1 and 4688 in the index's field names), 488 rows back; 2,500 results paged 1,000 at a time with none repeated; bad SPL, a revoked token, a wrong password and an unreachable host each reported. Rate limiting is covered by unit tests (`tests/test_splunk_client.py`): the lab Splunk wasn't made to refuse searches.

## Elastic

`shikari/query/elastic.py` (`ElasticClient`) runs ES|QL, as `shikari/build/elastic.py` writes it, through Elasticsearch's query API (`POST /_query`) and reads the rows back. There's no page or CLI command that runs it yet; Detection Validation's Elastic container uses it (`shikari/validation/docker_manager.py`).

```bash
export ELASTIC_URL=https://elastic.example.com:9200   # or ELASTIC_HOST (and ELASTIC_PORT, 9200)
export ELASTIC_API_KEY=...              # the encoded key; or ELASTIC_USERNAME and ELASTIC_PASSWORD
export ELASTIC_VERIFY=1                 # check the certificate; off by default for a lab's self-signed one
```

```python
from shikari.query.elastic import ElasticClient

r = ElasticClient().execute_query(esql, max_results=0)   # 0: every row
if r["status"] == "success":
    rows, stats = r["results"], r["stats"]   # stats: row_count, truncated, partial, pages, took_ms, run_duration
else:
    print(r["error"])                        # Elasticsearch's own message
```

- **Authentication**: an API key goes as `Authorization: ApiKey`; a username and password as basic auth.
- **ES|QL**: run as written. Its own `WHERE @timestamp >= NOW() - 1 day` is the window; the generated detections read the `logs-endpoint.events.*` data streams (Elastic Defend's names).
- **Paging**: ES|QL has no cursor. A query that returns events (no `STATS`, no `LIMIT` of its own, no `KEEP`, `DROP` or `RENAME`) is paged by `@timestamp` and `_id`, `page_size` rows a request (at most the cluster's `esql.query.result_truncation_max_size`, 10,000 by default), until `max_results`. Any other query runs once; `stats.truncated` says it came back full (its `LIMIT`, or ES|QL's default 1,000), and `stats.partial` that a shard didn't answer.
- **Errors are returned, not raised**: bad ES|QL (Elasticsearch's parser or verifier message), an unknown field, a wrong password, an expired or revoked key, a missing index privilege, a timeout, Elasticsearch unreachable. 429 and 503 are retried three times, honouring `Retry-After`.

### Validated

Against Elasticsearch 9.4.0 (the Docker image, security on, on the MacBook), 17 November 2026 ([#50](https://github.com/cmdaltr/shikari/issues/50)): the Windows 11 lab recording (`atomics-win11-20261109`) indexed as ECS through `DockerSIEMManager.ingest_lab_run`, 458,981 events into the process, file, registry and network streams in 54 seconds; a T1082 detection from `ElasticQueryGenerator` run through the manager returned its 100 summary rows (HOSTNAME.EXE 115 times from the lab's own runs); 1,308 process events paged in two requests and 25,000 registry events in three of 10,000, none repeated, past both the 1,000 default and the 10,000 cap; API-key and password authentication; bad ES|QL, an unknown field, a wrong password, a revoked key, a timeout and an unreachable host each reported. Rate limiting is covered by unit tests (`tests/test_elastic_client.py`). It ran from the MacBook's Shikari, not from inside Shikari's container as the Splunk run did.
